# D6 금칙어 검사 성능 개선

## 목적

메시지 전송 hot path에서 실행되는 금칙어 검사의 CPU 비용을 확인하고, 금칙어 판정 결과와 Socket.IO 계약을 유지하면서 처리 비용을 줄인다.

이번 D6 작업은 금칙어 검사 개선을 우선 범위로 한다. AI 기능 추가·변경은 진행하지 않으며, 파일 업로드 I/O와 단일·다중 노드 저장소 제약은 별도 측정에서 병목이 확인될 때 후속 검토한다.

## 기존 시나리오와 계약

금칙어 검사는 `ChatMessageHandler`의 메시지 저장 이전에 실행된다.

```text
chatMessage 수신
→ 사용자 조회
→ 방 조회 및 참여 여부 확인
→ 메시지 내용 파싱
→ BannedWordChecker.containsBannedWord()
→ 금칙어가 없으면 메시지 저장 및 전송
```

금칙어가 포함되면 메시지를 저장하지 않고 기존 Socket.IO 오류 계약을 유지한다.

```json
{
  "code": "MESSAGE_REJECTED",
  "message": "금칙어가 포함된 메시지는 전송할 수 없습니다."
}
```

기존 E2E의 `채팅방 생성 및 메시지 흐름`과 `파일 업로드 및 금칙어 검증` 시나리오 및 이벤트 payload는 수정하지 않는다.

## 문제

기존 `BannedWordChecker`는 메시지를 소문자로 변환한 후 금칙어 집합 전체를 순회하며 각각 `String.contains()`를 호출한다.

```text
시간 복잡도 ≈ 금칙어 수 × 메시지 검색 비용
현재 사전 크기 = 10,000개
금칙어 길이 = 4~10자
```

금칙어가 없는 정상 메시지는 조기 종료할 수 없어 매번 최대 10,000개를 모두 검사한다. 메시지 TPS가 증가하면 이 작업이 Socket.IO 메시지 처리 스레드의 CPU 점유와 tail latency를 높일 수 있다.

## 원인

- `Set`은 정확히 일치하는 문자열 조회에는 유리하지만 메시지 내부의 부분 문자열을 한꺼번에 찾는 데는 도움을 주지 못한다.
- 금칙어마다 메시지를 다시 검색하므로 금칙어 사전 크기에 비례해 검사량이 증가한다.
- 정상 메시지가 일반적인 서비스에서는 대부분의 요청이 최악 검사 경로를 통과한다.

## 확인 방법

실제 구현과 같은 알고리즘을 사용하는 일회성 Java 측정 코드를 `/private/tmp`에서 실행했다. 측정 파일은 제품 코드 및 Git에 포함하지 않는다.

측정 조건:

| 항목 | 값 |
|---|---:|
| 기준 커밋 | `c055ae8` |
| JVM | OpenJDK 26.0.1, 64-bit Server VM |
| 아키텍처 | arm64 |
| 금칙어 | 10,000개 |
| 워밍업 | 정상 메시지 2,000회 |
| 본 측정 | 유형별 10,000회 × 3라운드 |
| 정상 메시지 | 사전에 포함되지 않은 고정 문자열 |
| 차단 메시지 | 사전 단어 1개를 본문 가운데 포함한 고정 문자열 |

이 측정은 JMH와 같은 정식 마이크로벤치마크가 아니며, 금칙어 검사 알고리즘의 방향성을 비교하기 위한 로컬 기준값이다. 전체 메시지 처리시간이나 실제 Socket TPS로 해석하지 않는다.

### 개선 전 결과

| 유형 | 1라운드 | 2라운드 | 3라운드 | 안정 구간 해석 |
|---|---:|---:|---:|---:|
| 정상 메시지 | 346.14µs | 317.97µs | 318.13µs | 약 318µs/건 |
| 금칙어 포함 | 143.32µs | 144.18µs | 141.51µs | 약 142µs/건 |

정상 메시지 처리량은 안정 구간에서 약 3,143건/초였다. 금칙어 포함 메시지는 금칙어 집합 순회 중 일치 위치에 따라 결과가 달라질 수 있다.

## 개선 방법

애플리케이션 시작 시 금칙어 10,000개로 trie와 실패 연결을 한 번 구성하고, 요청 시에는 메시지 문자열을 한 번 순회해 여러 금칙어를 동시에 검색하도록 변경했다.

```text
기존: 메시지 1건 × 금칙어 최대 10,000개 개별 검색
개선: 시작 시 검색 구조 생성 + 메시지 1건당 문자열 1회 순회
```

- 금칙어 원본은 기존과 동일하게 `Locale.ROOT` 기준 소문자로 정규화한다.
- 메시지도 기존과 동일하게 `Locale.ROOT` 기준 소문자로 변환한다.
- 부분 문자열 포함 시 차단하는 기존 동작을 유지한다.
- 검색 구조는 생성자에서 완성된 이후 읽기만 하므로 요청 간 공유 상태를 변경하지 않는다.
- API URL, Socket.IO 이벤트, 오류 code/message는 변경하지 않는다.

## 개선 후 결과

동일한 사전·문장·반복 횟수로 개선 알고리즘을 측정했다.

| 유형 | 1라운드 | 2라운드 | 3라운드 | 안정 구간 |
|---|---:|---:|---:|---:|
| 정상 메시지 | 0.90µs | 0.58µs | 0.41µs | 약 0.41~0.58µs/건 |
| 금칙어 포함 | 0.53µs | 0.16µs | 0.16µs | 약 0.16µs/건 |

JIT 워밍업 영향으로 라운드별 차이가 있으므로 배수 자체를 전체 서비스 성능으로 일반화하지 않는다. 다만 금칙어 수 전체를 요청마다 순회하던 CPU 비용이 제거된 것은 코드 구조와 분리 측정에서 모두 확인된다.

## 기능 검증

기존 테스트만 실행했으며 테스트 코드는 추가하거나 수정하지 않았다.

```bash
cd apps/backend
./mvnw -Punit-tests test \
  -Dtest=BannedWordCheckerTest,ChatMessageHandlerTest
```

| 결과 | 값 |
|---|---:|
| 실행 테스트 | 5 |
| 실패 | 0 |
| 오류 | 0 |
| 건너뜀 | 0 |

확인된 기존 동작:

- 금칙어와 정확히 일치하는 메시지 차단
- 본문 중간에 금칙어가 포함된 메시지 차단
- 정상·null·공백 메시지에 대해 금칙어 없음 반환
- 채팅 핸들러의 금칙어 거부 및 정상 메시지 처리 계약 유지

전체 안정성 판정 전에는 기존 E2E의 금칙어 시나리오를 수정 없이 실행해야 한다.

### 기존 금칙어 E2E 실행 결과

E2E 파일을 수정하지 않고 금칙어 시나리오만 두 차례 실행했다.

```bash
BASE_URL=http://localhost:3000 pnpm --dir e2e exec playwright test \
  tests/chat.spec.js --grep '금칙어 포함 메시지'
```

- 결과: 두 실행 모두 1 failed
- 두 실행 모두 `chat.spec.js`의 `beforeAll` 사전 로그인 단계에서 중단됐다.
- 실패 위치: `loginAction()`의 `page.goto('http://localhost:3000/login')`
- 오류: `net::ERR_ABORTED`
- 금칙어 메시지 전송 및 `BannedWordChecker` 호출에는 도달하지 못했다.
- D4 기준선에서도 동일 위치와 오류가 반복됐으므로 D6 변경으로 새로 발생한 회귀 증거는 아니다.
- 기존 E2E 안정성 게이트가 통과하지 않은 상태이므로, 관련 단위·핸들러 테스트 통과와 분리해서 기록한다.

## 기대 효과

- 금칙어 10,000개 사전 전체 순회 제거
- 메시지 TPS 증가 시 금칙어 검사 CPU 사용량 증가 완화
- Socket.IO 메시지 처리시간과 p95/p99 악화 가능성 감소
- 사전 크기가 증가할 때 요청당 검사 비용이 사전 전체 크기에 직접 비례하지 않음

## 남은 검증 및 후속 후보

1. 기존 `page.goto('/login')` 오류가 해결된 환경에서 금칙어 E2E 재실행
2. 동일 메시지 부하 조건에서 개선 전후 Socket 메시지 p95/p99와 CPU 비교는 필요 시 추가 수행
3. 애플리케이션 시작 시 검색 구조 생성시간과 heap 증가량 확인
4. 파일 업로드 I/O timeout은 실제 부하에서 대기 또는 오류가 확인될 때 별도 개선
5. 로컬 파일 저장의 다중 노드 제약은 배포 토폴로지가 확정될 때 문서화

## 완료 조건

- 기존 금칙어 판정 결과와 Socket.IO 오류 계약 유지
- 기존 E2E 금칙어 시나리오 통과
- 동일 조건에서 금칙어 검사 CPU 비용 개선 수치 확보
- 전체 메시지 부하 결과에서 CPU 또는 p99 개선 여부를 과장 없이 구분해 기록
