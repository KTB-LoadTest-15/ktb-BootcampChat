# 방 목록 커서 페이지네이션

## 문제

기존 `GET /api/rooms`는 방이 몇 개이든 MongoDB에서 전체 문서를 읽고, 전체 방의 생성자·참여자와 최근 메시지 수를 조합해 한 번에 반환했다. 테스트 데이터가 누적될수록 한 요청의 DB 조회량, 응답 크기, 직렬화 비용이 함께 증가한다.

## 원인

응답의 `metadata`는 페이지 형태였지만 실제 조회는 `findAllByOrderByCreatedAtDesc()`였고, 프론트도 전체 결과를 한 번에 렌더링했다.

## 개선

- 기존 `GET /api/rooms` URL과 `data` 배열을 유지한다.
- 첫 요청은 최신 방 30개만 조회한다.
- 응답의 `metadata.nextCursor`가 있으면 `GET /api/rooms?cursor=...`로 다음 30개를 조회한다.
- 커서는 `createdAt + _id`를 URL-safe Base64로 인코딩한다.
- 정렬과 커서 조건을 지원하도록 `{ createdAt: -1, _id: -1 }` 복합 인덱스를 사용한다.
- 한 페이지에 대해서만 사용자와 최근 메시지 수를 일괄 조회한다.
- `limit`은 1~100 범위로 제한한다.

커서 페이지네이션에서는 전체 개수를 세지 않아 `metadata.total`과 `totalPages`를 `-1`로 반환한다. `currentCount`, `hasMore`, `nextCursor`를 페이지 진행 기준으로 사용한다.

## 확인 방법

1. 방을 31개 이상 준비한다.
2. 첫 요청의 `data`가 최대 30개이고 `hasMore=true`, `nextCursor`가 존재하는지 확인한다.
3. 다음 커서 요청 결과가 첫 페이지와 중복되지 않는지 확인한다.
4. 모든 페이지를 합쳤을 때 최신순 정렬과 전체 ID 집합이 유지되는지 확인한다.
5. 잘못된 커서는 400을 반환하는지 확인한다.
6. 동일한 방 개수와 부하 조건에서 기존 전체 조회와 첫 페이지의 응답시간·응답 크기·MongoDB 실행시간을 비교한다.

## 기대 효과

방 개수가 증가해도 최초 목록 요청에서 처리하는 방 수를 최대 30개로 제한한다. 생성자·참여자 조회와 최근 메시지 집계 범위도 동일하게 줄어 초기 응답시간과 네트워크 전송량이 전체 방 개수에 비례해 증가하는 문제를 완화한다.
