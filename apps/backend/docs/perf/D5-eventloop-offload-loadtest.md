# D5 — 이벤트 루프 오프로드 실부하 A/B 검증 (loadtest)

> 목적: 마이크로 실측(쿼리 2→1, 워커 오프로드/순서/거부)에 더해, **실제 동시접속 부하에서 종단 지표**로
> 웹소켓 개선 효과를 확인한다.
> 방법: baseline(이번 세션 이전 커밋 `f14b6eb`)과 HEAD(`b9faba9`)를 각각 새로 빌드해 동일 env로 실행,
> `loadtest/load-test.js`로 동일 시나리오를 걸어 비교.

## 1. 방법론

- **빌드**: git에서 `f14b6eb`(개선 전)과 `b9faba9`(개선 후, 이번 세션 6커밋) 각각 `mvnw package`.
- **런타임(양쪽 동일)**: 로컬 Mongo/Redis(docker), JDK25, `MESSAGE_STORE=mongo`(메시지 저장 변수 배제), flush off, 시크릿 고정.
- **부하**: `load-test.js --users=1000 --batch-size=50 --batch-delay=300 --messages=20` (1000 동접, 공격적 램프로 포화 유도). 각 빌드 1회. 매 실행 전 워밍업(admin 로그인+방 생성)으로 콜드스타트 전이 제거.
- **비교 지표**: 클라이언트측(연결 시간, 메시지 p99, 에러 수, 전송량) + 서버 actuator(`socketio_*`).

## 2. 결과 — heavy (1000 users)

| 지표 | BASELINE (f14b6eb) | HEAD (b9faba9) | 변화 |
|---|---:|---:|---|
| 평균 연결 시간 | **16,812 ms** | **129 ms** | **−99.2%** |
| Auth 에러 | 173 | **0** | 제거 |
| 접속 성공 유저 | 828 / 1000 | **1001 / 1000** | 전원 접속 |
| Connection 에러 | 288 | 200 | −31% |
| 메시지 전송량 | 11,540 | **16,000** | **+39%** |
| P99 메시지 지연(성공분) | 2 ms | 2 ms | 동일 |
| Total 에러 | 552 | 504 | 구성 상이(아래) |

**해석(메커니즘 일치)**: baseline은 @OnEvent 핸들러의 블로킹 DB 작업이 event-loop 스레드를 점유해, 1000명이 몰릴 때 **신규 핸드셰이크·인증이 뒤로 밀려 평균 연결에 16.8초, 173건 auth 실패, 172명이 아예 접속 실패**했다. HEAD는 그 처리를 워커 레인으로 오프로드해 **event-loop이 핸드셰이크/인증에 자유로워** 연결이 129ms로 establish되고 전원 접속·throughput +39%를 달성했다. (메시지 자체 p99는 양쪽 2ms — 성공한 메시지의 처리 자체는 원래 빠르다. 개선은 "연결이 되느냐"에서 갈렸다.)

## 3. 부하 미포화 구간 — medium (200 users) (참고)

| 지표 | BASELINE | HEAD |
|---|---:|---:|
| 평균 연결 시간 | 164 ms | 85 ms |
| P99 메시지 지연 | 1 ms | 5 ms |
| Total 에러 | 0 | 0 |

**미포화에서는 차이가 노이즈 수준**이고, 오프로드가 워커 핸드오프 비용만큼 메시지 p99를 아주 약간(1→5ms, 둘 다 무시할 수준) 올린다. 오프로드의 이득은 **event-loop이 포화되는 고부하에서만** 나타난다(이론과 일치).

## 4. 정직한 단서와 한계

- **HEAD의 메시지 백프레셔**: 서버 `socketio_messages_errors_total{dispatch_rejected}=10414`. 이 공격적 버스트(1000명×batch50×delay300)에서 워커 레인 큐(기본 `queue-capacity=1000`)가 차서 초과 메시지를 `SERVER_BUSY`로 **의도대로 흘려보냈다**(순서 보장 위해 인라인 실행 안 함). 즉 baseline은 "연결 붕괴"로, HEAD는 "연결 유지 + 초과 메시지 셰딩"으로 과부하를 흡수했다. **레인 수(`socketio.worker.lanes`)/큐 용량(`socketio.worker.queue-capacity`) 튜닝이 다음 과제**(측정 게이트).
- **HEAD `session_null=782`**(baseline 18): 접속 유저가 훨씬 많아진 데다 과부하 중 세션 churn이 겹친 것으로 추정. 별도 확인 필요.
- **환경 노이즈**: 단일 노트북에서 다른 docker 스택(talktalk, loadharbor worker)이 동시 구동 중 → 절대 수치는 프로덕션 급 아님. 부하 클라이언트도 단일 node 프로세스라 1000 소켓에서 클라이언트측 한계가 일부 에러에 섞임. 단 **동일 클라이언트로 두 빌드를 재므로 delta는 유의미**.
- **1회 측정**(평균화 안 함). 방향성 근거로는 충분하나, 값 고정에는 반복 측정 권장.

## 5. 결론

마이크로 실측(쿼리·오프로드 단위테스트)에 더해, **실부하에서 이벤트 루프 오프로드가 고동접 시 연결 establish/인증을 붕괴에서 구제**함을 종단 지표로 확인했다(평균 연결 16.8s→129ms, auth 실패 173→0, 전원 접속, throughput +39%). 남은 과제는 워커 레인/큐 용량의 부하 기반 튜닝이다.
