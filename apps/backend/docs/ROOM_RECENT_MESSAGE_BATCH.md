# 방 목록 최근 메시지 수 배치 조회

## 문제

`GET /api/rooms`는 각 방의 최근 30분 메시지 수를 응답에 포함한다. 기존 구현은 방 목록을 순회하며 방마다 저장소를 한 번씩 조회했다.

- 방이 `R`개이면 최근 메시지 수 조회도 `R`회
- 동시 요청이 `V`개이면 최대 `R × V`회
- Artillery가 방을 계속 생성하고 정리하지 않으므로 테스트를 반복할수록 비용 증가

## 원인

공통 응답 매핑 메서드 안에서 `countRecentMessages(roomId)`를 호출해 목록 조회가 N+1 형태가 됐다. Redis 모드에서는 방마다 `ZCOUNT` 네트워크 왕복이 발생하고, Mongo 모드에서는 방마다 별도 count 쿼리가 발생했다.

## 확인 방법

동일한 방 개수와 최근 메시지 데이터로 `GET /api/rooms`를 단독 호출해 다음을 비교한다.

- MongoDB command 수와 응답 시간
- Redis command 수, 네트워크 왕복 시간과 응답 시간
- API 응답의 방별 `recentMessageCount` 값
- 같은 조건의 Artillery 성공률, p95, p99

## 개선 방법

- MongoDB: 대상 방 전체를 `$match`하고 `room`으로 `$group`하는 집계 쿼리 1회
- Redis: 방별 `ZCOUNT`를 pipeline 하나에 담아 네트워크 왕복 1회
- 방 생성/입장 이벤트처럼 방 하나만 필요한 경로는 기존 단건 조회 유지
- API URL과 응답 형식은 변경하지 않음

## 기대 효과

방이 100개일 때 Mongo count 요청은 `100회 → 집계 1회`가 된다. Redis 명령 자체는 정확한 방별 값을 위해 100개가 필요하지만 네트워크 왕복은 `100회 → pipeline 1회`로 줄어든다. 따라서 방 수가 누적될수록 커지던 목록 응답 지연과 동시 요청 시 저장소 연결 점유를 완화할 수 있다.

실제 개선 폭은 데이터 수, Redis/Mongo 네트워크 거리, 동시 요청 수에 따라 달라지므로 배포 전후에 같은 부하 조건으로 재측정한다.
